# 온라인 전환 계획 (인계 문서)

새 세션에서 이 문서와 `CLAUDE.md`, `docs/rules.md`, `docs/open-questions.md`만 읽어도 이어서 작업할 수 있게 정리한 문서.
(작성 시점: 규칙 엔진·핫시트 UI·휴리스틱 AI 완료, 테스트 184개 통과)

## 1. 목표와 범위

- **1차: Node 서버.** 지금의 TypeScript 엔진(`src/engine/`)을 서버에서 **그대로** 돌린다. 규칙을 두 군데 구현하지 않기 위해서다.
- **2차(나중): Java Spring 이식 검토.** 규칙이 굳은 뒤에 한다. 이식 기준은 `src/engine/data/*.json`과 엔진 테스트다.
- 1차 범위: **방장이 방을 열고**, 2~5명이 방에 들어와 각자 브라우저로 한 판을 끝까지 하는 것. AI 자리도 서버에서 돌린다.
- 이번 범위 밖: 계정·랭킹·매칭·결제, 모바일 앱, 관전.
- 시작 브랜치: **`main`**에서 `online/server` 브랜치를 따서 시작한다 (규칙 작업은 모두 `main`에 병합되어 있다).

## 2. 지금 있는 것

- `src/engine/` — UI와 무관한 순수 규칙 엔진. 서버에서 그대로 import 가능하다.
  - `createGame({ seed, civIds })` → 초기 상태
  - `apply(state, action)` → **새** 상태 (내부에서 `structuredClone`, 규칙 위반은 `RuleError`를 던진다)
  - `actorOf(state)` → 지금 입력해야 하는 문명 id (전투 배치·대상 선택 때는 아직 안 낸 쪽)
  - `aiStep(state)` → AI가 한 번 행동한 새 상태와 그 행동. `aiCandidates`로 후보 목록도 얻는다.
  - 난수는 상태 안의 시드(`state.rng`, mulberry32)라서 **같은 시드 + 같은 행동 열 = 같은 결과**다. 서버 재시작 후 행동 로그로 복원할 수 있다.
  - `data/*.json` — 문명·지형·자원·기술 트리·군사 카드·불가사의·정책·타일 160장. 코드가 아니라 데이터다.
- `src/ui/` — React 핫시트 화면. `GameScreen.tsx`가 `apply`를 직접 부르고 `history`로 되돌리기, `localStorage`로 자동 저장한다.
- 행동은 모두 JSON이다 (`src/engine/types.ts`의 `Action` 유니온, 약 25종): `buildCity`, `placeWorkers`, `research`, `produce`, `upgrade`, `invest`, `declareWar`, `arrangeBattle`, `chooseTargets`, `recallGeneral`, … 서버로 그대로 보내면 된다.
- 한 판은 최대 180라운드(`MAX_ROUNDS`)까지, 승자가 없으면 무승부(`winner === null`, `phase === 'over'`).
- 전투가 끝날 때마다 `state.battleReports`에 결과가 남는다(최대 30개). 화면의 전투 장면이 이걸 쓴다.

## 3. 온라인에서 새로 필요한 것

### 3.1 권한 검사
- 행동을 보낸 사람이 지금 그 행동을 할 차례인지 서버가 확인한다. 기준은 `actorOf(state)`.
- 예외: `arrangeBattle`·`chooseTargets`는 `playerId`를 직접 받는다. 서버는 "그 `playerId`가 보낸 사람 본인인지"와 `state.battle` 상태(배치 단계에서 아직 안 낸 쪽인지)를 확인한다.
- `apply`가 던지는 `RuleError`는 그 사람에게만 오류로 돌려주고 상태는 바꾸지 않는다.

### 3.2 비공개 정보 걸러 보내기 (가장 중요)
핫시트에서는 가림막으로 가렸지만 온라인에서는 **서버가 문명별 뷰를 만들어 보내야** 한다. `view(state, playerId)` 함수를 새로 만든다.

| 정보 | 공개 범위 |
|---|---|
| 타일·기술·정책·불가사의·도시 구성·점령 상태 | 공개 |
| 군사 카드의 **장수**와 종류(이름) | 공개 |
| 군사 카드의 **공격 방향** (`CardInst.dirs`) | 본인만. 전투가 끝난 뒤 `battleReports`에는 나온다 |
| 손에 든 타일 (`Player.hand`), 두 번째 도시용 `pendingCity` | 본인만 |
| 정찰로 본 타일 `scouted`, 맡아둔 타일 `held` | 본인만 |
| 전투 중 놓은 자리 `battle.slots` | 양쪽이 모두 낸 뒤에야 공개. 그 전에는 "냈다/안 냈다"만 |
| 전투의 `picks` | 해당 단계가 끝나기 전까지 본인만 |
| 타일 덱 `deck`(순서), 난수 `rng` | 비공개. 클라이언트에는 남은 장수만 |
| 로그 | 공개. 단, 방향이 들어가면 안 된다 (지금도 "무엇을 생산했는지"만 남긴다) |
| 불가사의 투자 `investments` | 공개 (결정됨, 3.4) |

테스트: 한 문명의 뷰에 상대의 `hand`, `dirs`, `deck`, 낸 `slots`가 **절대** 들어 있지 않다는 테스트를 먼저 쓴다.

### 3.3 동시에 하는 부분
- 일꾼 배치부터 식량 정산까지는 우선도 순으로 **한 명씩** 한다(엔진 규칙). 나머지 사람은 기다리거나 관전한다.
- 전투의 카드 배치는 양쪽이 **각자 동시에** 낸다(`arrangeBattle`). 서버는 둘 다 받을 때까지 상대 배치를 숨긴다.
- 라운드 정산(불가사의, 전투)은 엔진이 자동으로 이어 간다.

### 3.4 결정된 운영 규칙 (사용자 확정)
1. **불가사의 투자 금액은 공개**한다.
2. **방장이 방을 연다.** 방장이 방을 만들고 참가자를 받고 게임을 시작한다.
3. **되돌리기는 방장만** 할 수 있다 (온라인에서도 핫시트의 되돌리기를 방장 권한으로 유지).
4. **시간 제한 없음.**
5. **재접속 가능.** 같은 링크·토큰으로 들어오면 같은 자리로 복귀한다.
6. **접속이 끊기면 무제한 기다린다.** AI 대행·건너뛰기 없음.
7. **방장은 중간에 방을 폭파**(강제 종료)할 수 있다.
8. **방 인원은 최대 5명** (2~5명). 핫시트 시작 화면의 2~6명과 다르다.
9. **관전자 없음.** 방에 들어온 사람은 모두 한 자리의 플레이어다.

구현에서 챙길 점:
- 되돌리기는 서버가 `행동 기록`에서 마지막 행동을 빼고 `createGame(seed)`부터 다시 `apply`해서 복원한다. 엔진이 결정적이라 가능하다. 되돌리면 이미 상대에게 공개된 정보(정찰한 타일, 공개된 전투 배치)가 되돌아가므로, 되돌릴 수 있는 범위(마지막 사람 행동 하나 / 현재 단계까지)를 정한다. 방장이 직접 책임지는 기능이니 제한은 느슨하게 둔다.
- 무제한 대기와 재접속 때문에 **서버가 재시작되어도 방이 살아 있어야** 한다. 행동 기록과 방 정보(참가자 토큰, 시드, 문명 선택)를 저장소에 남긴다.
- 방장이 나가도 방은 유지한다(방장은 재접속 가능). 방을 없애려면 방장이 폭파를 눌러야 한다. 폭파하면 모든 접속을 끊고 저장된 기록을 지운다.
- 시작 후에는 새 사람이 들어올 수 없다. 재접속 토큰을 가진 사람만 들어온다.
- 문명 선택: 방장이 시작하기 전에 자리별 문명을 정하거나 각자 고르게 한다 (아직 미정 — 구현 때 정해도 된다).

## 4. 제안 구조 (1차)

- 새 폴더 `server/` (Node 22 + TypeScript, `src/engine`을 import). `ws`(WebSocket) 또는 Socket.IO + 가벼운 HTTP(방 만들기).
- 상태 저장: 우선 메모리 + 행동 로그를 파일/SQLite에 추가 저장 → 재시작 시 `createGame(seed)`에 행동을 다시 `apply`해서 복원한다 (엔진이 결정적이라 가능).
- 메시지 예 (JSON):
  - 클라 → 서버: `{ "type": "action", "action": { ...Action } }`, `{ "type": "join", "room": "...", "token": "..." }`, 방장 전용 `{ "type": "undo" }`, `{ "type": "closeRoom" }`, `{ "type": "start" }`
  - 서버 → 클라: `{ "type": "state", "view": <view(state, playerId)>, "seq": 123 }`, `{ "type": "error", "message": "..." }`
- 클라이언트: `GameScreen`의 `dispatch`를 "서버로 전송"으로, `game`을 "서버가 준 뷰"로 바꾼다. 가림막·되돌리기·자동 저장은 온라인 모드에서 끈다. 핫시트 모드는 그대로 둔다.
- 엔진은 가능한 한 **고치지 않는다.** 필요한 변경은 `view` 함수, 그리고 서버가 쓸 수 있게 `state`를 JSON으로 직렬화·복원하는 확인 정도다 (상태는 현재 순수 JSON이라 문제 없음).

## 5. 작업 순서 제안

1. **M0 시작**: `main`에서 `online/server` 브랜치를 딴다 (병합은 이미 끝남).
2. **M1 뷰 필터**: `view(state, playerId)` + 비공개 정보 테스트. 엔진 쪽 순수 함수라 서버 없이 먼저 만든다.
3. **M2 최소 서버**: 방장이 방 만들기, 참가자 입장(최대 5명), 방장이 시작, 행동 수신 → `apply` → 각자 뷰 전송, 방장의 되돌리기·폭파. AI 자리 서버 실행. 서버 쪽 테스트(가짜 클라이언트 여럿으로 한 판 진행).
4. **M3 클라이언트 연결**: `GameScreen` 온라인 모드. 전투 배치·결과 창은 기존 컴포넌트를 재사용.
5. **M4 재접속·저장**(시간 제한은 없음). 서버 재시작 후에도 방 복원.
6. **M5 사람 둘로 한 판 완주**(Playwright로 두 브라우저), 그 뒤 정리.

## 6. 알려진 규칙·밸런스 현황 (온라인과 별개로 남은 일)

- 열린 질문 목록: `docs/open-questions.md` (해결된 항목은 취소선). 남은 것: 전투기·탱크·폭격기의 "타일 보유 도시" 자원이 석유가 맞는지(35번) 등.
- AI 시뮬레이션 관찰(참고): 2인전은 과학·문화 승리가 비슷하게 나온다. 아폴로는 한 차례에 과학 20이 필요해서 자유 정책 + 식량 전부 과학 변환이 필요하다. 문화 승리의 상당수는 상대 도시가 모두 사라져서 끝난다.
- 아르테미스 사원, 합리주의, 군사 카드 비용 등 수치는 사용자가 직접 조정 중이다. **사용자가 준 숫자는 임의로 바꾸지 않는다.**
- `README.md`의 "AI 시뮬레이션으로 확인한 것" 문단은 오래됐다 (온라인 작업 때 같이 갱신).
